Если пайплайны CI/CD пишутся на Kotlin Script (`.main.kts`), возникает вопрос: как проверить, что скрипт вообще скомпилируется, не запуская его целиком?

Именно эту проблему решает **kts-compiler** — утилита, которая проверяет компилируемость `.main.kts` файла без реального запуска. Изначально появилась как внутренний инструмент в Plata-банке. Сейчас веду и дорабатываю её в личном репозитории: [github.com/xvar/kts-compiler](https://github.com/xvar/kts-compiler).

## Как это устроено внутри

```
.main.kts файл
      │
      ▼
[1] Парсинг заголовка
    ищем @file:DependsOn(...) и @file:Repository(...)
    (обычный текстовый разбор, компилятор ещё не запускается)
      │
      ▼
[2] Резолвинг зависимостей → classpath
      │
      ├── совпало с кэшем (по хэшу координат) ──▶ взять classpath из кэша
      │
      └── кэш-промах ──▶ скачать через Maven-резолвер, положить в кэш
      │
      ▼
[3] Kotlin embeddable compiler, compile-only
    (собираем .class, но НЕ вызываем main() —
     именно это отличает проверку от запуска)
      │
      ▼
[4] Диагностики компилятора → exit code
    0 — компилируется, чужой код CI может ехать дальше
    1 — печатаем ошибки построчно, CI падает на этом шаге
```

Дальше — по шагам.

**Парсинг заголовка.** Скрипт не запускается и даже не компилируется целиком на этом этапе — просто читаются верхние строки файла в поисках аннотаций `@file:DependsOn(...)` и `@file:Repository(...)`. Это быстрее, чем сразу отдавать файл компилятору, и позволяет сначала понять, какой classpath вообще нужен.

**Резолвинг зависимостей.** По найденным координатам собирается classpath. Результат резолвинга кэшируется по хэшу набора координат — если зависимости не менялись между запусками (типичная ситуация в CI, где скрипт правится, а импорты нет), classpath берётся из кэша, и сеть не трогается вовсе.

**Компиляция без запуска.** Это и есть главный трюк. Kotlin Scripting API позволяет получить откомпилированные классы отдельно от их выполнения — `compiler.compile(...)` возвращает `ResultWithDiagnostics`, не вызывая `evaluator.eval(...)`. Обычный `kotlinc` в режиме скрипта компилирует и тут же выполняет `main()`; kts-compiler останавливается на шаге компиляции и просто не делает следующий.

**Диагностики.** Если компиляция прошла — exit code 0, CI едет дальше. Если нет — диагностики компилятора (файл, строка, колонка, сообщение) печатаются в stdout построчно, exit code 1 — понятная точка отказа в логах пайплайна, без побочных эффектов от реального запуска непроверенного скрипта.

*Кэш зависимостей и диагностики компилятора — то, чего не хватало в первой черновой версии этой статьи.*
